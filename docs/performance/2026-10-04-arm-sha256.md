# ARM SHA256 acceleration

Starting revision: `33596fa855ec1b8fd92f12b719979c27bdce233a`.
Only `SHA256::transform` gains an accelerated path: four-word hardware rounds
with a rolling four-vector message schedule. MD5, digest formatting, streaming,
padding and public interfaces are unchanged. The scalar transform is retained
verbatim, with no new dependencies or build flags.

## Target selection

Acceleration requires AArch64, `__ARM_FEATURE_SHA2`, and little-endian byte
order. The [Arm ACLE SHA2 feature contract](https://arm-software.github.io/acle/main/acle.html#sha2-extension)
identifies support in the configured compiler target. This is a compile-time
selection, not runtime CPU detection. Generic Android/Linux targets that do not
require SHA2 retain the portable implementation; no global `+crypto` flag is
added. The measured default Apple ARM64 target enables the accelerated path.

The [Arm intrinsic explanation](https://developer.arm.com/community/arm-community-blogs/b/tools-software-ides-blog/posts/porting-putty-to-windows-on-arm)
was used to check round-state and message-schedule ordering.

## Measured effect

517 preloaded real charts, 73,152,865 bytes, one worker, seed 12345. Apple Clang
21, C++17 `-O3 -DNDEBUG`, same benchmark harness. Each mode uses separate
baseline/candidate/candidate/baseline processes; one warmup per process is
excluded and medians pool six measured rounds per variant. Measurements ran
06:12:04–06:13:15 UTC after all builds and equivalence checks finished and
before production validation or pushes. CI was complete; process inventories
showed an idle runner listener and no worker/build/test processes.

| Mode | Starting CPU ms | Accelerated CPU ms | CPU reduction |
| --- | ---: | ---: | ---: |
| Full | 1710.090 | 1423.030 | 16.79% |
| Scan | 1253.280 | 957.407 | 23.61% |
| Metadata | 1168.955 | 859.345 | 26.49% |

Wall-time reductions were 16.81%, 23.55% and 26.52%, respectively. These are
parser-process measurements on this target, not application-wide predictions.
No fresh comparison with the earlier `2b964abd` parser is claimed.

The public hash-wrapper microbenchmark improved by 5.76× for 64-byte inputs,
9.76× for 4 KiB and 10.22× for 1 MiB. Checksums matched in every round.
Targets selecting the scalar path do not receive this acceleration.

## Verification

- Clean production modular/resource/Python-comparison and regenerated
  amalgamation suites pass, including new exact-sized unaligned input tests
  at offsets 1, 3 and 15 with 129, 257 and 65,537 bytes.
- Production hash vectors, streaming and unaligned-input tests pass under
  native Clang ASan/UBSan/float-cast-overflow, portable Clang (`-march=armv8-a`),
  portable GCC 15 and SHA2-enabled GCC 15.
- SHA source compile checks pass for macOS x86, iOS ARM64, and Android NDK
  28.2 ARM64 both with the default portable target and an explicit SHA2 test
  target. These are source compile checks, not device-runtime tests.
- 11,075 ASan/UBSan equivalence checks pass: known answers including one million
  `a` bytes, random binary inputs/chunks/alignment, 1,000 random compression
  states, and padding/counter boundaries. Actual streamed 512 MiB−1, 512 MiB
  and 512 MiB+1 inputs match the starting implementation.
- 5,170 parser snapshots match: 517 charts × Full/Ready/Metadata/Scan/
  Scan-reference × two seeds. Serialized metadata includes both MD5 and SHA256;
  chart timing and structure are unchanged in every compared snapshot.
- Independent parser and application-adoption static reviews found no issues.

The existing SHA implementation encodes only the low 32 message-length bits in
final padding; this optimization deliberately retains its behavior at and above
512 MiB. It does not replace the hash wrapper with an implementation that would
silently change such identities. Addressing that existing limitation requires a
separate compatibility decision.

[Raw measurements, compiler/source hashes, equivalence probe and validation commands](experiments/2026-10-04-arm-sha256-results.json)
record the evidence. Application adoption, exact generated-file checksums and
full build/CTest results are recorded in the application's current parser handoff.
